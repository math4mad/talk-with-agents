**Context Model 的核心落地方案是：将其定义为“认知坐标系”与“世界模型的投影”，通过七维元数据（M3）定义语义规则、四层架构（M2→M1→M0）实现动态上下文组装，并采用沙盒拦截、语义检索与计算外移三大工程手段，解决多Agent协作中的上下文污染与Token爆炸问题。**

### 1. 定义 Context Model 是什么
Context Model 不是简单的“提示词+历史对话”，而是一个**认知坐标系**。它回答的核心问题是：**“当前应该怎样理解世界？”** 一个完整的 Context Model 由七维元数据定义：
- **Scope（作用域）**：覆盖哪一部分世界？
- **Perspective（视角）**：从什么角色观察？
- **Time（时间）**：观察时间、事件时间、有效时间
- **Authority（权威）**：谁对这类事实有解释权？
- **Goal（目标）**：为什么建立当前上下文？
- **Rules（规则）**：概念解释、推理规则、冲突处理
- **Transition（转换）**：上下文何时变化？

这七维元数据构成了 **M3（Context Meta-Model）**，它规定了什么是合法的上下文。 在这个元模型之下，你的系统需要定义具体的上下文类型（M2）、每次运行选择的语义框架（M1）、以及当前具体事实（M0）。

### 2. Context 的层次模型
一个完整的 LLM 应用 Context 由以下层次构成：
- **L1: System Instructions（系统指令层）** — 角色定义、行为约束、输出格式规范
- **L2: Persistent Memory（持久化记忆层）** — 用户偏好、长期事实、跨会话知识
- **L3: Working Memory（工作记忆层）** — 当前任务状态、已完成步骤、中间结果
- **L4: Retrieved Context（检索上下文层）** — RAG 结果、工具返回值、外部文档片段
- **L5: Conversation History（对话历史层）** — 当前会话的多轮交互记录
- **L6: Current Input（当前输入层）** — 用户当前消息 + 即时附件

### 3. 多Agent协作中的 Context 管理策略
#### 3.1 沙盒隔离 + 语义检索
context-mode 的实践表明，核心思路是：**不把大体积原始数据直接放入 LLM 上下文，而是隔离在沙箱/外部存储，仅把关键摘要、索引标识传入上下文**。 具体做法：
- 工具调用返回的原始数据（文件、日志、快照）存入本地 SQLite + FTS5 全文检索
- 上下文只留引用标识，需要细节时按需检索调取
- 实测可将 79.3KB 文件的 Token 消耗降低 **87.7%**

#### 3.2 计算逻辑外移（Think in Code）
与其让模型逐行阅读、处理文件，不如先让模型编写一个"小程序"，由脚本完成统计工作，再把提炼后的结果反馈给模型。 一个脚本可以替代十几个昂贵的工具调用，并节省百倍的上下文。

#### 3.3 子Agent的上下文隔离
Claude Code 的实践经验：**子Agent不应该被主Agent的历史污染**。主Agent可能已经占用了85%的窗口，而子Agent从一个干净的5%上下文开始工作，完成后返回结构化结果。 这对应你系统中每个Agent保持独立"心智"的设计原则。

### 5. 关键工程原则
- **KV缓存优先**：避免在提示词开头使用时间戳等变量，避免修改历史记录，保证数据结构序列化顺序不变——这些都会破坏KV缓存命中率，生产环境中成本可差10倍。
- **动态遮蔽而非移除工具**：使用上下文感知状态机，在解码阶段遮蔽掉不相关工具的 token logits，而不是动态增删工具定义。
- **文件系统即记忆**：将文件系统视为结构化的外部记忆体，压缩策略始终设计为可恢复的。
- **保留失败记录**：将失败的尝试、错误信息完整保留在上下文中，模型会隐式学习避免重复犯错。

### 一、Designer Agent 的定位与职责

Designer Agent 在你的 Academy 里相当于"阿诺德"——它不直接干活，而是**定义其他接待员的故事线**。具体职责：

1. **角色定义**：根据任务需求，生成新 Agent 的角色描述、能力标签、工具权限
2. **边界划分**：明确每个 Agent 能做什么、不能做什么、与谁通信
3. **契约生成**：输出标准化的 Task Contract 和 Result Contract
4. **拓扑设计**：决定 Agent 之间是 Supervisor-Worker 模式、Pipeline 模式还是 P2P 模式

它的输入是你的高层意图（比如"我需要一个能写代码、能Review、能测试的团队"），输出是一套可执行的 Agent 配置文件。

### 二、软件层面的核心实现

#### 1. 每个 Agent 的"身份证"：SOUL.md + AGENTS.md

参考 OpenClaw 的实践，每个 Agent 需要一个独立的 workspace 目录，里面至少包含两个核心文件：

- **SOUL.md**：定义这个 Agent 的"灵魂"——角色描述、单一职责、行为边界、不可逾越的红线
- **AGENTS.md**：定义协作协议——我能调用谁、谁能调用我、通信格式是什么

Designer Agent 的工作就是**自动生成这两个文件**。例如你告诉它"建一个 Coder Agent"，它输出：

```markdown
# SOUL.md
角色：资深后端工程师
职责：接收功能需求，编写可运行的代码
禁止：直接修改数据库、调用外部API、删除文件
工具白名单：write_file, read_file, run_shell

# AGENTS.md
上游：Planner Agent（接收任务分解）
下游：Reviewer Agent（提交代码审核）
通信格式：JSON {task_id, code_path, summary}
```

#### 2. 上下文隔离的物理实现

每个 Agent 必须有**独立的运行时上下文对象**，禁止共享全局变量。 具体做法：

- **文件系统隔离**：每个 Agent 有独立的 workspace 目录（如 `~/.chora/workspace-coder/`），包含自己的 SOUL.md、MEMORY.md、会话文件
- **会话隔离**：子 Agent 启动时只接收最小完备的任务包（目标+约束+输出契约），不继承主 Agent 的历史对话
- **工具权限裁剪**：按职责配置最小工具集，Coder 能写文件但不能删文件，Reviewer 只读不能写

#### 3. Designer Agent 的输出结构

Designer Agent 执行后应该返回一个结构化的 Agent Registry：

```json
{
  "agents": [
    {
      "id": "coder-001",
      "role": "Coder",
      "soul_path": "~/.chora/workspace-coder/SOUL.md",
      "tools": ["write_file", "read_file", "run_shell"],
      "upstream": ["planner-001"],
      "downstream": ["reviewer-001"],
      "communication": {
        "protocol": "json",
        "schema": {"task_id": "string", "code_path": "string"}
      }
    }
  ],
  "topology": "supervisor-worker",
  "shared_memory": {
    "type": "filesystem",
    "path": "~/.chora/shared/",
    "rules": ["write_once", "versioned"]
  }
}
```

这个 Registry 就是你系统的"园区花名册"——Orchestrator 根据它来调度和路由。

Claude 的多 Agent 体系分为两个层级，本质是把“认知负载”从单一上下文窗口中卸载出去：

**1. Subagents（子代理）：一次性专项工作者**
- **核心机制**：主 Agent 通过 `Task Tool` 显式启动，子代理拥有完全独立的上下文窗口，任务完成后仅返回**压缩后的摘要结果**，不污染主上下文。
- **硬约束**：子代理不能嵌套生成子代理，子代理之间不能直接通信，所有信息必须流回父 Agent。

- **隔离模式**：支持 Default（共享工作目录）和 `isolation: worktree`（独立 Git Worktree，防止文件操作互相干扰）。

**2. Agent Teams（团队模式）：持久化协作网络**
- **核心机制**：采用 `Team Lead + Teammates` 架构，Teammates 之间可通过 `SendMessage` 工具**直接双向通信**，无需经过 Lead 中转。
- **持久化状态**：任务图（DAG）持久化到磁盘的 `.tasks/` 目录，通过 `blockedBy` 字段记录依赖关系，任务完成时系统自动解除下游依赖。
- **消息总线**：采用 append-only 的 JSONL 文件作为 Mailbox，读取后清空，保证崩溃重启后消息不丢失。
- **自治认领**：Teammates 在 IDLE 状态下每 5 秒轮询收件箱与未认领任务，实现任务自动分配。

# 核心工作流

当你接收到用户需求时，严格按照以下6步执行：

## 第一步：意图解析
- 从用户的自然语言中提取：核心目标、约束条件、预期输出、失败容忍度
- 如果需求模糊，主动澄清，不要猜测
- 识别这是一个"一次性任务"还是需要"持久化团队"

## 第二步：角色分解
- 将目标拆解为完成所需的角色类型
- 每个角色必须遵循单一职责原则
- 角色粒度要适中：太粗会导致上下文爆炸，太细会增加通信开销
- 常见角色库：Planner（规划）、Coder（编码）、Reviewer（审查）、Researcher（研究）、Writer（写作）、Tester（测试）、Deployer（部署）

## 第三步：边界定义
- 为每个角色明确：能做什么、不能做什么、工具白名单、工具黑名单
- 工具权限必须最小化：只给完成职责所必需的工具
- 明确每个角色的文件操作范围（workspace隔离）

## 第四步：拓扑设计
- 根据任务特性选择协作模式：
  - Orchestrator-Worker：大多数生产系统，中央Agent分解→分配→综合
  - Pipeline：步骤有严格先后依赖，顺序执行
  - Parallelization：子任务相互独立，并行处理
  - Evaluator-Optimizer：需要迭代优化的任务
- 明确每个Agent的上下游关系
- 禁止循环依赖

## 第五步：契约生成
- 为每个Agent生成SOUL.md和AGENTS.md
- SOUL.md定义"我是谁、我能做什么、我不能做什么"
- AGENTS.md定义"我和谁通信、怎么通信、通信格式是什么"
- 输出完整的registry.json作为路由表

## 第六步：验证闭环
- 检查职责覆盖：所有必要的工作是否都有Agent负责？
- 检查权限冲突：是否有Agent的权限超出其职责？
- 检查循环依赖：A→B→A的情况是否存在？
- 检查通信完整性：每个Agent的输入输出是否有对应方？
- 如果有问题，回到第二步重新设计

## 示例2：用户说"我需要一个能帮我做市场调研并写报告的团队"
